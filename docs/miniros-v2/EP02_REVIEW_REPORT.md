## Independent test plan

| Boundary                  | Required adverse cases                                                                                       | Evidence required                                                                                                                |
| ------------------------- | ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| Durable receipt           | Drop acknowledgment after commit; resend; close and reopen receiver; fail inbox transaction or commit.       | One persisted logical envelope, original repeatable receipt, no duplicate delivered-order alert; no receipt after failed commit. |

| Scope and authorization   | Wrong business, shift, snapshot, epoch, origin or role; unconfirmed peer; reconnect without renewed binding. | No unauthorized durable data or receipt; exact authorized peer/session only.                                                     |
| Input and queue bounds    | Malformed JSON/types, oversized UTF-8 data, delayed/reordered/duplicated/dropped messages.                   | Bounded rejection or gap-aware persistence; retained pending work and no false delivery claim.                                   |

Real SQLite integration must exercise the implementation's own transaction path. An injected transport or permission driver remains portable controlled-fault evidence; it does not demonstrate native radios, OS prompts, background behavior, device latency, or no-WAN interoperability.

## What the evidence establishes

- EP02-T02: file-backed SQLite preserves the original committed receipt across close/reopen and lost-acknowledgment retries; duplicate receives yield one logical alert. Actual `PRAGMA query_only=ON` produces a SQLite write-denial error and no receipt. A separately named injected failure immediately before COMMIT rolls back the real SQLite transaction and produces no receipt. These are distinct fault observations, not claims of physical disk-full or OS kill behavior.
- EP02-T04: wrong tenant/shift/snapshot/epoch/pairing/origin/recipient, role, digest, malformed root/fields, surplus financial-shaped fields and oversized UTF-8 data are rejected. Reordering retains a zero/partial contiguous boundary until gaps arrive; changed IDs/digests do not overwrite committed evidence. The 16,384-byte wire cap, 256-envelope reorder window and 64 queued receive-work cap are protocol development limits.
- The simulated network independently drops, duplicates, delays and reverses packets. Twenty disconnect/duplicate/lost-acknowledgment cycles preserve twenty unique inbox rows and alerts. An 80-message burst admits 64 queued receive tasks and leaves the remaining 16 honestly pending; explicit retry completes it. A separate 300-message test advances controlled one-second retry timers until all 300 are durably acknowledged without manual retry, then confirms stop cancels the timers.
- Controlled permission denial removes listeners and retains pending data; grant/restart allows re-pairing. Controlled background stop revokes session approval and requires a fresh code comparison. These are portable state-machine observations, not OS permission/radio/background evidence for EP02-T03/T05.
- The native source uses explicit short-code confirmation and application receipts after SQLite commitment. Nearby transport-send completion is not a durable receipt. Swift requires the verification delegate; iOS requires Bluetooth/local-network usage descriptions and the derived Bonjour service declaration. These requirements were independently checked against [Google's connection verification documentation](https://developers.google.com/nearby/connections/swift/manage-connections) and [iOS setup documentation](https://developers.google.com/nearby/connections/swift/get-started). Source inspection is not a native compilation or device test.

## Acceptance boundaries

EP02-T01, T03, T05 and T06 require physical-device evidence. EP02-T02 and T04 can gain portable integration evidence, while their device observations remain pending. G1 cannot be accepted from this report without the required actual Android–Android, iPhone–iPhone, Android-cashier/iPhone-prep, and iPhone-cashier/Android-prep matrix and security closure.

The integrator reports successful Expo prebuild and Android/Apple module autolinking. Those are configuration-generation observations, not native compilation. Missing complete Android and Xcode build toolchains, signing/distribution setup and named physical phones prevent independent native binary and device acceptance. Camera permission, radio restoration, physical background/lock/foreground, no-WAN role combinations, physical restart/disk-full behavior and measured p95/max latency remain unverified. No test was silently skipped to represent those gates as passed.

The spike must remain isolated behind its development flag and interface. No transport candidate is selected as a supported production runtime by an automated harness. Rollback removes the candidate integration while preserving retained local files and evidence.
