## Implemented behavior

- `initialV2Projection(snapshot, actor)` creates a deeply frozen, unopened, tenant/shift/snapshot/cashier-epoch projection. Stock starts as zero observations until the explicit opening operation supplies all snapshot count lines; no central stock, purchase or warehouse mutation exists.
- `applyV2Operation(snapshot, projection, operation, actor, hash)` verifies strict snapshot/operation shape and canonical SHA-256 digests through shared helpers, then checks trusted cashier identity, installation, role, tenant, shift, authority epoch, allowed operation kind, projection identity and frozen snapshot binding before any effects. Canonical journal operations are always cashier-authored. A valid digest is not a signature or grant check: actual Ed25519 verification belongs to the trusted EP05 adapter.
- Exact original operation ID/body/digest/sequence retries reproduce the projection before terminal/sequence rejection. A changed canonical body under the same ID raises a visible conflict. Revalidated authenticity can differ while the signed operation body remains identical; the adapter still must authorize it. New operations require `lastSequence + 1`; device timestamps never determine order.
- All effects apply to a deep clone; any later failure leaves the caller's projection untouched. Successful output, nested orders/lines, closing evidence and summaries are deeply frozen.
- Opening requires exactly every snapshot item and no Uncounted lines. Explicit Counted(0) and Not brought both initialize zero stock but remain distinct in the immutable operation evidence. Initializer validates snapshot structure; asynchronous snapshot digest verification occurs before the first operation can take effect.
- Sales use only frozen product/recipe/modifier pricing and consumption. Gross sales are before discounts; `discountsMinor` is retained separately; net sales subtract discounts and refunds. Discounts cannot exceed subtotal. Sum of retained tenders must equal the exact total; only cash can have change, and change cannot exceed tendered cash. Consumption, payment totals and order counters commit together in the pure result; insufficient stock rejects the whole result.
- Refunds are bounded cumulatively by the original sale's retained cash or manual-digital tender, never by cash handed over before change. Cash refunds require enough expected cash. Refunds do not alter stock or prep state. Complimentary consumption and bounded original-line remakes consume stock without creating revenue. Remake product/modifier composition and per-command quantity must fit original lines; a distinct later authorized remake remains a separate audited usage event.
- Restock, waste and authorized stock adjustment preserve explicit operation reasons; adjustments require the trusted actor's `ADJUST_STOCK` capability and an adapter-verified approval matching approval ID, exact operation ID, item and delta; an arbitrary payload approval UUID is insufficient. Inventory/cash arithmetic uses existing overflow-safe integer helpers. Insufficient stock/cash rejects negative results; there is no silent overselling override.
- Prep transitions require an exact adapter-verified command assertion matching command ID, sale, prep installation and action; the prep installation must differ from the cashier. Valid steps are New → Making → Done. Replayed stable commands have no repeated business effects, and an old Start cannot undo Done. A reused command ID with a changed payload conflicts.
- A return requires an adapter-verified `unprepared-return` command, a distinct prep installation, original order still New, and the explicit physical-return declaration. It restores the full original recorded consumption once, marks the order Cancelled, and does not reverse money. Refund is separate. Neither caller-supplied booleans nor a bare command UUID constitutes prep verification.
- Close matches the entire pre-close journal digest and sequence boundary, expected cash/net sales/all expected stock exactly. Actual counts preserve all count statuses, including Uncounted; actual cash can remain null. Every unresolved New/Making order requires one explicit manual resolution, with no unrelated resolution IDs. Pending attachments remain declared independently. New commands after close reject; exact original operation retries remain safe.
- `summaryV2(projection)` returns gross/discount/refund/net totals, net tender breakdown, expected drawer cash and a frozen stock copy. It does not invent physical observations or claim cloud completeness.

## Review and integration notes

The first fixed shared type lacked a separate discount total. This agent flagged the gross/net ambiguity; the integrator added `discountsMinor` to projection/summary before freeze, and the reducer/tests now preserve conventional gross-before-discount semantics. The first return payload had only booleans and a UUID; this agent requested a trusted verification boundary before implementing it. No SHA-256-only authorization claim is made. The trusted adapter must verify grants, signatures, prep assertions and stock-approval assertions against its authorized records. The pure reducer intentionally performs no networking, storage, signature-key lookup or UI side effects.
