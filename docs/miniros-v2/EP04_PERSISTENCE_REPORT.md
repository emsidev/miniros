# EP04 — Native ledger persistence report

## Scope and result

Implemented the isolated v2 ledger repository under `apps/mobile/src/storage/v2/`, using the frozen EP03 contracts and the root-owned additive migrations. The native adapter targets installed `expo-sqlite` 57.0.2. The portable implementation has actual file-backed SQLite integration and process restart evidence. Native SDK compilation, physical cold starts and device storage failures remain blocked; this report does not count desktop SQLite results as device acceptance.

No POS flow or EP06 UI was added. No branch, commit, remote project operation, deployment, database reset or deletion of retained operational evidence was performed. Temporary test databases alone are removed by test cleanup.

## Implementation

- `connection.ts` owns one explicitly opened connection. Every connection sets and reads back WAL, `synchronous=FULL` and `foreign_keys=ON`. A short SQLite busy timeout plus bounded asynchronous retries allows another actual connection to release a held writer transaction. Each connection serializes its callbacks; `BEGIN IMMEDIATE` and database uniqueness constraints arbitrate competing connections. The transaction result is returned only after successful COMMIT. A failed response after COMMIT remains recoverable through operation deduplication.
- `expo.ts` opens a separate native connection with `useNewConnection: true`; it wraps the installed asynchronous `execAsync`, `runAsync`, `getAllAsync` and `closeAsync` APIs. Inspection of `apps/mobile/node_modules/expo-sqlite/src/SQLiteDatabase.ts` found that `withExclusiveTransactionAsync` creates another connection and begins before invoking its callback. The ledger therefore owns and configures its actual transaction connection directly. The `.web.ts` adapter explicitly refuses a browser durability substitute.
- `migrate.ts` applies missing additive migrations and `user_version` inside one transaction. Failure rolls back the migration and preserves the same file and old version. A database newer than the app fails safely without rewriting it. Recovery is to retain the file and retry with a corrected/newer application; there is no drop/recreate path. Root-owned migration v1 creates scopes, snapshots, projection, journal, tenders, drafts, both outboxes and receipts; v2 adds attachment jobs. Composite foreign keys and immutable evidence triggers apply to the actual connections used by repository operations.
- `repository.ts` scopes every access by account, business, installation, shift and authority epoch. It stores a verified immutable snapshot and checks the trusted actor before effects. The repository rechecks visible identity around asynchronous work and before returning results. Explicit logout/lock and account/business/device switches deny foreign access while retaining evidence. It never deletes pending work on auth changes.
- Drafts are versioned compare-and-swap records with stable IDs and immutable kinds. Snapshot, checklist, item, product, recipe and modifier references are validated. Packing, opening and cart state retains typed distinctions, including counted zero and uncounted. A sale/opening may consume only its matching committed draft revision and contents, inside the financial transaction; the draft JSON remains retained. Failure leaves the previous committed revision untouched.
- A financial commit writes the immutable operation and original local receipt, cached projection, original sale tender evidence, peer reference, cloud reference, matching draft status and optional media references atomically. Same-ID retries compare the canonical operation body and return the original local receipt without repeating financial or stock effects. Changed payloads conflict. An uncertain response does not mint a different receipt or consume another draft.
- Peer and cloud receipts are independent, checked against their exact operation and authorized through the required receipt adapter. Queue attempts retain bounded machine error codes. Attachment jobs have their own IDs, references and monotonic pending/uploaded/linked states; upload failure does not reverse local or remote financial acknowledgement. No transport or media upload worker is implied by these repository APIs.
- Readiness uses actual database integrity and readback: a count guard precedes journal pages of 64 records; every operation and local receipt is verified, the projection is reconstructed and compared, original tender contents and both outbox references are checked, and pending destinations/media are counted independently. The cached projection has a 16 MiB byte guard before fetching JSON, drafts have a 256 KiB guard, journal capacity is 10,000 operations per retained shift, and public queue pages are capped at 500. Capacity errors preserve records and require reconciliation; there is no automatic pruning. Full projection replay remains proportional to retained history and is a readiness operation, not a per-keystroke action.
- Diagnostics export only bounded state/count metadata, with no account IDs, names, payloads, signatures, media URIs, credential material or free-form errors.

## Required authority boundary

`LedgerRepository` requires constructor-injected `StorageAuthority` methods for current identity, snapshot authorization, operation authorization and receipt authorization. These methods are trusted adapter context, never read from an operation's own claimed role or approval fields. Structural validation and SHA-256 digest verification do not establish authenticity. There is no permissive production default authority; the synthetic authority appears only in test fixtures.

The persistence layer has no online access-token or grant-clock expiry hard stop. A prepared local capability must remain usable during an online-token outage; explicit local logout/lock does deny access. The future enrollment, secure-key lifecycle and local capability adapter are EP07 work. EP05's signature-verification boundary can provide authenticated operation context, but this EP04 report does not claim an installed enrollment flow or secure private-key storage. Readiness replay requires the authority adapter to authorize retained historical evidence, including verified prep and stock-approval records where those operations require them.

`pending(scope, "peer")` exposes cashier-scoped operation evidence to a trusted transport adapter. It is not a prep-device financial mirror or a role-redacted wire protocol. The future peer adapter must apply the frozen role-minimal contract; a prep actor cannot open this cashier repository.

## Device/staging boundary

The environment has no Android SDK/adb/JDK, full Xcode, CocoaPods or attached test phones. SQLite engine integration and OS process-kill tests are I evidence. They do not prove native Expo filesystem persistence under app termination, flash/power failure, lock-screen transitions, background suspension or low-storage conditions. The EP04-T01/T04 D portions and physical G2 storage acceptance remain blocked pending native release builds and device execution. There is no staging or pilot acceptance claim.
